# Job Mute MVP PRD

## 전제 점검

Wanted 채용 공고 목록에서 보기 싫은 공고를 숨기는 Chromium 기반 확장 프로그램은 MVP로 적절하다. 이 문제는 서버, 계정, 백엔드 추천 시스템 없이도 content script가 페이지 DOM을 읽고 수정하는 방식으로 검증할 수 있다. Chrome 확장 문서 기준으로 content script는 웹페이지의 DOM을 읽고 변경할 수 있으며, `chrome.storage.local`은 확장 삭제 전까지 로컬 데이터를 저장한다.

단, 전제가 완전히 확정된 것은 아니다. Wanted는 SPA, 무한 스크롤, 동적 클래스명, A/B 테스트를 사용할 수 있으므로 실제 DOM 구조와 라우팅 변화에 따라 카드 탐지 안정성이 달라질 수 있다. 이 리스크의 초기 확률은 약 35%로 본다.

## 다양한 관점이 필요한 이유

이 제품은 단순 필터 UI가 아니라 채용 탐색 흐름, 브라우저 권한, 개인정보 신뢰, 외부 사이트 DOM 안정성이 동시에 영향을 주는 확장 프로그램이다. 따라서 제품 가치만 보고 범위를 잡으면 구현 안정성이나 권한 리스크를 놓칠 수 있고, 기술 구현만 보고 시작하면 사용자가 실제로 원하는 “다시 보고 싶지 않음”이라는 문제를 좁게 해결할 수 있다.

| 후보                      | 설명                                                               | 적합 확률 |
| ------------------------- | ------------------------------------------------------------------ | --------: |
| 로컬 규칙 기반 DOM 숨김   | 회사명, 공고명, 키워드 규칙을 로컬 저장하고 Wanted 페이지에서 숨김 |       75% |
| 계정/클라우드 동기화 포함 | 여러 기기 동기화, 로그인, 백업 포함                                |       15% |
| AI 자동 분류              | 공고 내용을 분석해 자동 숨김                                       |        7% |
| 네트워크 요청 차단        | Wanted API 응답 자체를 가공하거나 차단                             |        3% |

최종 MVP 접근은 로컬 규칙 기반 DOM 숨김이다. 개인정보/권한/운영 비용을 낮추면서 가장 빠르게 사용자 가치를 검증할 수 있기 때문이다.

## 문제 정의

Wanted를 반복적으로 사용하는 구직자는 관심 없는 회사, 공고, 직무 조건, 키워드를 계속 마주치며 탐색 시간이 늘어난다. Job Mute의 MVP 문제는 “사용자가 직접 지정한 원치 않는 공고를 브라우저 로컬 기준으로 다시 보지 않게 하는 것”이다.

MVP에서는 추천 품질 개선, 지원 이력 관리, 회사 평가, 다중 채용 플랫폼 통합은 다루지 않는다.

## 대상 사용자

주 대상 사용자는 Wanted를 데스크톱 Chromium 브라우저에서 반복적으로 사용하는 구직자다. 특정 회사, 공고, 헤드헌팅성 문구, 계약 형태, 기술 키워드를 피하고 싶은 사용자에게 가장 적합하다.

비대상 사용자는 모바일 앱 중심 사용자, 여러 채용 플랫폼 통합 관리를 원하는 사용자, AI 추천/자동 판별을 기대하는 사용자다. 확장 프로그램 설치 허들이 있으므로 초기 사용자는 불편이 명확한 파워 유저일 가능성이 약 70%로 높다.

## 사용자 시나리오

1. 사용자는 Wanted 채용 공고 목록을 연다.
2. 보기 싫은 공고 카드에서 `숨김` 버튼을 누른다.
3. 확장 프로그램은 해당 공고를 즉시 목록에서 숨기고 로컬 저장소에 기록한다.
4. 사용자는 팝업 또는 옵션 화면에서 숨김 규칙을 확인, 수정, 삭제한다.
5. 이후 같은 공고, 회사명, 키워드가 포함된 항목은 자동으로 숨겨진다.
6. 상세 페이지에서도 현재 공고나 회사를 숨김 규칙으로 추가할 수 있다.

## MVP 기능

### 1. 공고 숨기기

Wanted 목록 페이지의 각 공고 카드에 숨김 액션을 제공한다.

요구사항:

- 공고 카드 단위로 `숨김` 버튼을 노출한다.
- 클릭 시 공고 ID, 제목, 회사명, URL, 숨김 시각을 로컬 저장소에 저장한다.
- 저장 직후 해당 카드를 숨긴다.
- 새로고침과 재방문 후에도 같은 공고는 숨긴다.

근거와 불확실성:

- 공고 ID가 URL 또는 DOM에서 안정적으로 추출되면 가장 정확한 숨김 단위가 된다.
- 공고 ID 추출이 모든 목록 유형에서 가능한지는 실제 Wanted DOM 검증이 필요하다. 불확실성은 약 30%다.

### 2. 회사 숨기기

사용자가 특정 회사의 모든 공고를 숨길 수 있어야 한다.

요구사항:

- 목록 카드 또는 상세 페이지에서 `이 회사 숨기기` 액션을 제공한다.
- 회사명 기반 매칭을 적용한다.
- 숨긴 회사명은 관리 화면에서 삭제할 수 있다.

근거와 불확실성:

- 사용자가 반복적으로 피하고 싶은 대상은 개별 공고보다 회사 단위일 가능성이 높다.
- 회사명 문자열 매칭은 단순하지만 표기 변형, 계열사명, 동일/유사 회사명 오탐 가능성이 있다.
- MVP에서는 정규식, 별칭, 고급 조건식을 제외하고 단순 키워드 기반으로 시작한다.

### 3. 키워드 숨기기

사용자가 직접 입력한 키워드가 공고 제목, 회사명, 화면상 노출 텍스트에 포함되면 숨긴다.

요구사항:

- 옵션 화면에서 제목 키워드와 회사 키워드를 추가/삭제한다.
- 입력값은 공백 제거, 빈 문자열 제거, 대소문자 비구분 처리를 한다.
- 키워드 규칙 변경 후 목록 페이지에 즉시 반영한다.

근거와 불확실성:

- 사용자가 피하고 싶은 기준은 “파견”, “계약직”, “헤드헌터”, 특정 기술명처럼 다양할 수 있다.
- 자유 키워드는 AI 자동 분류보다 설명 가능성이 높고 구현 비용이 낮다.
- Wanted 화면에 모든 매칭 대상 텍스트가 DOM으로 노출되지 않을 수 있다. 불확실성은 약 25%다.

### 4. 숨김 규칙 관리

확장 팝업 또는 옵션 화면에서 숨김 상태를 복구할 수 있어야 한다.

요구사항:

- 숨긴 공고 목록을 보여준다.
- 공고별 숨김 해제를 지원한다.
- 전체 초기화를 지원한다.
- 제목 키워드와 회사 키워드를 관리한다.
- 현재 페이지가 Wanted가 아닐 경우 지원 사이트가 아님을 표시한다.

근거:

- 실수로 숨긴 공고를 복구할 수 있어야 제품 신뢰가 생긴다.
- 전체 초기화는 초기 MVP에서 지원 비용을 낮추는 안전장치다.

### 5. 목록과 상세 페이지 적용

Wanted 목록 페이지와 상세 페이지 양쪽에서 동작해야 한다.

요구사항:

- 목록에서는 매칭되는 공고 카드를 숨긴다.
- 상세 페이지에서는 현재 공고가 숨김 대상이면 안내 배너를 표시한다.
- 상세 페이지에서 현재 공고 또는 회사를 숨김 규칙으로 추가할 수 있다.
- SPA 라우팅 변화와 무한 스크롤로 추가되는 카드에도 적용한다.

근거와 불확실성:

- Wanted는 동적 렌더링 가능성이 높으므로 최초 로드 시점만 처리하면 누락이 생길 수 있다.
- `MutationObserver` 기반 재스캔이 필요할 가능성이 높다.
- 과도한 DOM 감시는 성능 저하를 만들 수 있으므로 debounce/throttle이 필요하다.

## 비기능 요구사항

### 개인정보와 권한

- 서버 전송을 하지 않는다.
- 로그인 정보, 쿠키, 지원 이력, 프로필 정보를 수집하지 않는다.
- 숨김 규칙은 브라우저 로컬 저장소에만 저장한다.
- 권한은 `storage`와 Wanted 도메인 host permission으로 제한한다.
- `<all_urls>` 권한은 사용하지 않는다.

근거:

- Chrome 확장 권한은 확장이 손상됐을 때 피해 범위를 줄이기 위해 제한적으로 선언해야 한다.
- Chrome 문서상 host permission은 확장이 특정 URL과 상호작용하기 위한 권한이다.
- 사용자가 입력한 숨김 키워드 자체가 민감할 수 있으므로 외부 전송 금지가 핵심이다.

### 성능

- 목록 100개 카드 기준 숨김 적용 300ms 이내를 목표로 한다.
- 스크롤 중 눈에 띄는 지연이 없어야 한다.
- DOM 변경 감지는 debounce 또는 throttle을 적용한다.
- 오류가 발생해도 Wanted 페이지의 본래 기능을 방해하지 않는다.

초기 성능 목표의 신뢰도는 약 60%다. 실제 Wanted DOM 규모와 렌더링 방식 확인 후 조정한다.

### 안정성

- Wanted DOM 변경 시 확장 전체가 실패하지 않도록 방어적으로 파싱한다.
- 공고 ID 식별 실패 시 제목과 회사명 fallback을 고려한다.
- 동적 클래스명에만 강하게 의존하지 않는다.
- 숨김 처리 CSS는 Wanted UI와 충돌하지 않도록 확장 전용 class name을 사용한다.

### 호환성

- Chrome 최신 안정 버전을 1차 지원 대상으로 한다.
- Chromium 기반 Edge는 가능하면 지원하되 MVP 검증은 Chrome 우선이다.
- Firefox와 Safari는 MVP에서 제외한다.

## 제외 범위

MVP에서 제외한다:

- 계정 생성과 로그인
- 클라우드 동기화
- 여러 기기 백업
- AI 기반 공고 분류
- 지원 이력 연동
- Wanted 외 채용 사이트 지원
- 공고 추천/랭킹 기능
- 회사 리뷰/평판 데이터
- 네트워크 API 응답 조작
- 모바일 앱 지원
- 팀/조직 공유 차단 목록
- Chrome Web Store 정식 배포 자동화
- 고급 정규식/조건식 필터

의도적 tradeoff:

- 로컬 전용 저장은 여러 기기 동기화를 포기하는 대신 개인정보, 권한, 서버 운영 리스크를 크게 낮춘다.
- 키워드 매칭은 오탐이 있을 수 있지만 AI 분류보다 설명 가능하고 빠르게 검증할 수 있다.
- Wanted 전용으로 제한하면 확장성은 낮지만 MVP 검증 속도가 빠르다.

## 성공 지표

제품 성공 지표:

- 설치 후 7일 내 숨김 규칙 1개 이상 생성 비율 50% 이상
- 주간 활성 사용자 중 숨김 동작 사용 비율 40% 이상
- 숨긴 공고가 다시 노출됐다는 보고 비율 5% 이하
- 7일 내 확장 삭제율 30% 이하

기능 품질 지표:

- 목록 페이지 숨김 적용 성공률 95% 이상
- 상세 페이지 숨김/추가 액션 성공률 90% 이상
- 주요 페이지 콘솔 오류 없음
- 페이지 로딩과 스크롤 체감 저하 없음

리스크 지표:

- 권한 경고로 인한 설치 이탈
- Wanted DOM 변경 후 기능 실패
- 사용자가 왜 숨겨졌는지 이해하지 못하는 비율

## 오픈 질문

1. 공고 숨김의 기본 키는 공고 ID만으로 충분한가?
   - 추천: 공고 ID 우선, 실패 시 제목+회사명 fallback.
2. 숨긴 공고는 완전히 제거할 것인가, 접은 상태로 표시할 것인가?
   - 추천: MVP는 완전 숨김. 복구는 관리 화면에서 제공.
3. 상세 페이지에서 숨김 대상 공고에 접근하면 어떻게 처리할 것인가?
   - 추천: 본문을 막기보다 상단 안내 배너와 `이번만 보기` 액션 제공.
4. 회사 숨김은 독립 기능으로 둘 것인가, 회사 키워드 필터로 통합할 것인가?
   - 추천: MVP 구현은 회사 키워드로 통합하되 UI 문구는 `회사 숨김`으로 제공.
5. Chrome Web Store 배포를 MVP 완료 조건에 포함할 것인가?
   - 추천: 1차 MVP는 unpacked extension 검증까지로 제한하고, 스토어 배포는 다음 단계로 둔다.

## 현재 구현과의 차이

현재 저장소는 WXT, TypeScript, Manifest V3 기반의 기본 구조를 갖고 있으며, 공고 카드 탐지, 공고 단위 숨김, 로컬 저장, 팝업에서 숨김 해제, 옵션 페이지에서 제목/회사 키워드 저장을 이미 포함한다.

추가 확인이 필요한 항목:

- 실제 Wanted 목록 페이지에서 `/wd/:id`, `/jobs/:id` 링크 패턴이 충분한지 확인한다.
- 상세 페이지에서 현재 공고를 식별하고 숨김/배너를 제공하는 기능을 추가한다.
- 회사 숨김을 명시적 액션으로 제공할지, 회사 키워드 입력으로 충분한지 결정한다.
- MutationObserver 재스캔이 스크롤 성능에 미치는 영향을 측정한다.
- 권한 선언이 Chrome Web Store 심사와 사용자 신뢰 관점에서 충분히 좁은지 검토한다.
